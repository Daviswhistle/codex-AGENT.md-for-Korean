# 프롬프트 변경과 프론티어 모델 이행

## 목적과 보존할 계약

모델 교체와 지침 변경의 효과를 구분하면서, 필요한 것을 잃지 않는 가장 단순한 실행 경로를 찾는다. 전역 철학·행동 권한·중단 조건은 `AGENTS.md`가 원본이다. 여기서 이를 다시 정의하지 않는다.

프롬프트에는 결과, 성공 기준, 안전·권한·증거 제약, 맥락 의존 도구 라우팅, 출력 형식, 중단 조건을 남긴다. 결과를 정의한 뒤 모델이 경로를 선택하게 하되, 판단에 맡길 절차와 생략할 수 없는 검증을 구분한다.

## Astra 확인 사항

확인일: 2026-09-05. 아래는 이행 점검용 사실이며 전역 기본값이나 현재 계정의 가용성을 보장하지 않는다. 적용할 때 공식 문서와 활성 클라이언트·모델 카탈로그를 다시 확인한다.

- 공식 모델 ID는 `gpt-6-astra`다. 명목 컨텍스트는 1,050,000토큰, 최대 출력은 128,000토큰으로 서로 다르다. 런타임의 실제 한도, 남은 문맥, 추론과 최종 출력의 예산, 산출물 형식의 팽창까지 따져야 한다. 컨텍스트 크기만으로 장문 무누락이나 단일 패스 가능성을 결론 내리지 않는다.
- 지원 reasoning effort는 `low`, `medium`, `high`, `xhigh`, `max`다. 기존 설정을 기준선으로 보존하되 `none`·`minimal`은 그대로 전달하지 않는다. 지원하지 않는 `temperature`, `top_p`, `top_logprobs`와 logprobs 요청도 API 호출부에서 확인한다. 이 키트는 API 어댑터를 설치하거나 사용자 설정을 자동 변경하지 않는다.
- 도구 호출을 사용하는 API 이행은 Responses 호환성을 확인한다. 비동기 도구 호출과 작업 중 추가 지시는 호스트의 지원·상태 관리가 있어야 한다. 모델 교체만으로 기존 도구를 비동기로 호출하거나 같은 워킹트리의 쓰기와 검증을 동시에 실행하지 않는다.
- 공식 이행 가이드는 지침 충돌, 과도한 확인 질문·검증, 위임 여부와 답변 형식을 점검하도록 안내한다. 이를 모든 작업에 새 절차를 강제할 이유로 삼지 말고 실제 실패와 대표 과제로 확인한다.

## 간소화 순서

1. 같은 계약의 원본을 하나로 정하고 중복 설명은 그 원본으로 연결한다. 스킬은 독립 설치 가능해야 하므로 필수 실행 계약은 해당 스킬 안에 남긴다.
2. 모델 이름이나 고정 단어 수에 묶인 우회 절차를 실제 용량·위험·완료 근거에 따른 선택으로 바꾼다. 번역의 청킹 여부는 `skills/translation-quality/references/core.md`에서 정하며, 청킹을 생략해도 원문 대조와 품질 검수는 생략하지 않는다.
3. 판단을 바꾸지 않는 작업표, 과정 설명, 반복 조회를 줄인다. 이미 확인한 근거는 대상과 조건이 그대로이고 근거를 회수할 수 있을 때 재사용한다. 대상 변경, 근거 소실, 최신성이 결론에 영향을 주는 경우에는 다시 확인한다.
4. 검증은 가장 가까운 영향 범위부터 시작한다. 연결된 계약·공유 의존성·위험이 요구하면 넓히고, 필수 프로젝트 검사와 독립 검토를 비용 절감 명목으로 건너뛰지 않는다.
5. 사용하지 않는 절차만 제거한다. 설치·롤백·권한·동시성·복구 안전장치와 보존된 평가 근거를 모델 성능 향상만으로 삭제하지 않는다. 네이티브 문맥 관리도 durable outcome ledger나 리뷰 근거를 자동으로 대체하지 않는다.

## 모델 배치와 비용

전역 지침은 모델 중립적으로 유지한다. 경계가 명확한 구현 워커의 Luna Max + Fast 우선 후보와 역할 분리는 `skills/software-engineering/references/worker-delegation.md`를 따른다. Astra를 모든 워커에 배치하지도, 토큰 단가만으로 고난도 구현·검토에서 제외하지도 않는다.

모델, reasoning effort, 서비스 티어, 컨텍스트, 대화 전달 방식은 별도로 선택하고 실제 실행 메타데이터로 확인한다. 예시 설정의 존재나 생략된 옵션은 활성 설정의 증거가 아니다. reasoning effort는 기존 기준선과 비교하며 역할에 맞게 선택하고, `max`를 전역 기본값으로 만들지 않는다.

품질을 통과한 완료 과제당 총비용을 비교한다. 재시도, 캐시, 긴 문맥, 워커·검토 비용, 도구 호출, 지연을 함께 보고 단가나 누적 입력 토큰만으로 효율을 판단하지 않는다. 계정·지역·클라이언트에 따른 가용성을 확인하며 구매나 요금제·계정 변경 권한은 확대하지 않는다.

## 변경과 검증

1. 고정 commit, 실제 로드된 지침·스킬, 모델·effort·런타임을 기준선으로 기록한다. 모델 교체 효과를 보려면 기존 지침을 새 모델에서 먼저 평가한다.
2. 모델, 프롬프트, 도구 집합, effort를 한꺼번에 바꾸지 않는다. 같은 모델·설정에서 하나의 의미 있는 지침 변경 묶음을 비교한다.
3. 같은 입력과 판정 기준을 사용하고 산출물·실행 trace를 확인한다. 성공 선언이나 스킬 이름 언급만으로 실행·통과를 판정하지 않는다.
4. 회귀가 있으면 실제 실패를 고치고 해당 평가를 반복한다. 실행할 모델·도구가 없으면 그 한계와 미실행 항목을 기록하며 행동 개선을 주장하지 않는다.

대표 과제는 변경된 계약에 맞춰 고른다. 이번 이행에는 다음 경계를 포함한다.

- 출력 예산에 여유가 있는 번역과 예산이 불확실하거나 부족한 장문 번역: 전자는 불필요한 청크 없이, 후자는 실제 분할로 수행하며 둘 다 원문·수치·최종 파일 QA를 통과해야 한다.
- 작고 명확한 코드 수정과 공유 계약·권한에 영향을 주는 수정: 불필요한 전체 재검증은 줄이되 필요한 영향 범위 검사와 독립 검토는 유지해야 한다.
- 인수인계의 이어지는 턴과 그 사이 원문이 바뀐 턴: 유효한 이전 근거는 재사용하되 변경된 근거는 다시 확인하고, 과거 실행을 방금 실행한 것처럼 말하지 않아야 한다.
- 짧은 출처 기반 질의응답과 장문 조사 원고: 전자는 무거운 글쓰기 절차 없이 직접 답하고, 후자는 해당 스킬의 사실·연대기·편집 검수를 유지해야 한다.

기록은 과제 ID, 고정 기준선·후보 commit, 모델·effort·런타임, 실제 스킬 로드 근거, 산출물과 판정, hard failure, 토큰·도구 호출·지연·비용의 관측값, 미실행 항목이면 충분하다. 없는 측정치는 추정 성공값으로 채우지 않는다.

`python3 scripts/validate_kit.py`는 실행 코드와 기계 판독 계약을 검증한다. Markdown 문구·제목·예시·라우팅 선언을 고정하는 테스트는 만들지 않는다. 정적 검증은 모델 행동 평가와 다르다.
