# 기본 작업자 위임과 Luna Max Fast 예시

날짜: 2026-08-24

결정:

1. `software-engineering` 스킬은 주 세션이 요구 해석, 목적, 작업 경계, TCA/CRA 선택, 완료 판정, 최종 응답 책임을 유지한 채, 명확한 실행 계약으로 분리할 수 있는 구현과 로컬 검증을 `worker`에 기본 위임한다.
2. 같은 worktree에는 쓰기 가능한 worker를 한 번에 하나만 둔다. 병렬 구현은 격리된 worktree와 독립 검증 계약이 있을 때만 허용한다.
3. worker의 완료 선언만으로 끝내지 않고 주 세션이 실제 diff, 검증 결과, 남은 불확실성을 확인한다. 커밋, CRA, finding 판정, 다음 작업 gate는 기본적으로 주 세션이 맡는다.
4. 전역 지침과 스킬은 특정 모델, reasoning effort, service tier를 강제하지 않는다.
5. 선택적 런타임 예시로 `examples/codex/agents/worker.toml`을 제공한다. 예시는 `gpt-5.6-luna`, `max`, `fast`, `workspace-write`를 사용하지만 installer가 자동 적용하지 않는다.

배경:

주 세션이 직접 조사, 편집, 테스트 로그까지 모두 품으면 사용자의 요구와 완료 기준을 유지해야 할 문맥이 실행 소음으로 오염될 수 있다. 반대로 모든 작업을 무조건 위임하면 사소한 수정에도 조정 비용이 생기고, 잘못된 작업 계약이나 worker 요약의 무비판적 수용이 새 실패 지점이 된다.

따라서 위임의 기본 단위는 과업 전체가 아니라 명확한 목표, 범위, 제약, 권한, 검증, 완료 근거를 가진 하나의 coherent task unit으로 둔다. 주 세션은 실행을 분리하되 판단과 검증 책임을 넘기지 않는다.

Luna Max Fast는 범위가 좁고 반복 가능한 구현 작업에서 속도와 실행량을 우선하는 개인 런타임 예시다. model catalog, 계정 접근권, 비용, 지연 허용도는 사용자마다 다르므로 공개 키트의 규범적 기본값으로 승격하지 않는다.

직접 실행 폴백:

- 위임 비용이 작업보다 큰 사소한 변경
- 대화 중 핵심 선택과 구현을 분리할 수 없는 작업
- worker 또는 subagent 기능을 사용할 수 없는 환경
- worker 실패 후 직접 복구가 더 안전한 경우
- unrelated worktree 변경을 안전하게 분리할 수 없는 경우

나중에 다시 볼 조건:

- worker 위임이 실제 대표 과제에서 품질, 문맥 보존, 복구 가능성 중 어느 것도 개선하지 못할 때
- 반복적으로 작업 계약이 부족하거나 worker 결과 검증이 누락될 때
- 병렬 write worker를 안전하게 격리하고 통합하는 공통 실행 계약이 검증될 때
- Codex custom agent schema, 모델 식별자, reasoning effort, service tier 동작이 바뀔 때
