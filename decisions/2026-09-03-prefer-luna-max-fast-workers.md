# 실행 워커의 Luna Max + Fast 우선 선택

날짜: 2026-09-03

결정: 경계가 명확한 실행 워커는 Luna Max + Fast로 완료 기준을 충족할 수 있는지 먼저 검토하고, 가능하면 이 조합을 사용한다. 더 강한 모델은 작업 난도, 오류 비용, 모호성 또는 독립성 때문에 Luna Max + Fast가 부족하다는 구체적인 품질 근거가 있을 때 선택한다. 이 우선순위는 실행 워커에만 적용하며 전역 모델 기본값이나 독립 reviewer의 기본값으로 확장하지 않는다.

배경: 기존 계약은 역할, 모델, reasoning effort, service tier, context, fork를 실행 전에 선택하도록 했지만 실행 워커의 첫 후보는 정하지 않았다. 사용자는 현재 비용 우선순위에서 Luna Max의 비용 대비 품질을 선호하며, Luna Max 실행 워커에는 Fast의 추가 사용량을 기본으로 허용했다. 이 선택이 가능한 핵심 전제는 Sol 주 세션이 제품 의도와 모호성을 먼저 해결하고 범위와 검증을 구체화해, Luna worker가 판단을 재구성하는 대신 경계가 명확한 실행에 집중하게 한다는 것이다. 첫 후보를 명시하지 않으면 일반적인 품질 선호나 편리한 full-history 상속만으로 더 비싼 모델을 선택할 수 있다.

경계:

1. 완료 기준을 충족할 수 있다는 판단은 작업 계약, 오류 비용, 예상 증거량, 필요한 검증에 근거한다.
2. 주 세션은 제품 의도, 모호성, 범위, 검증을 먼저 정리해 정밀한 실행 계약을 만든다. 이 준비가 부족하면 계약을 보완하거나 읽기 전용 탐색을 먼저 수행하며, 모호한 인계를 더 강한 worker로 보상하지 않는다.
3. 높은 오류 비용, 넓은 공개 계약, 중요한 권한·보안·금전 판단, 독립 검토처럼 더 강한 모델이 필요한 역할은 구체적인 근거를 기록하고 상향할 수 있다.
4. Fast 기본 선택은 현재 계정의 기존 사용량 안에서만 유효하며 구매, 요금제, quota, provider 또는 계정 설정 변경을 허가하지 않는다.
5. launcher가 Luna, Max reasoning 또는 Fast를 실제로 표현하지 못하면 호환되는 launcher를 사용하거나 선택 기록을 실제 profile로 수정한다. 설정 누락을 Fast 활성으로 간주하지 않는다.
6. Luna Max + Fast custom worker 예시는 계속 opt-in으로 두며 installer가 자동 설치하거나 기존 `worker.toml`을 덮어쓰지 않는다.

2026-07-16의 전역 모델 중립 원칙은 유지한다. 이 결정은 2026-08-24와 2026-09-02 결정에서 Luna Max + Fast를 단순 선택지로만 두었던 부분을 실행 워커의 우선 후보로 좁게 갱신한다.

대안:

1. 모든 역할에 Luna Max + Fast를 강제한다.
2. 실행 워커도 모델 중립 선택만 유지하고 첫 후보를 정하지 않는다.
3. 모든 비사소한 작업에 Sol을 사용해 품질 상한을 우선한다.
4. Fast는 매 invocation마다 추가 비용 승인을 다시 판단한다.

이유: 주 세션이 어려운 판단과 계약 구체화를 맡으면 worker 모델은 이미 정리된 범위 안에서 구현과 로컬 검증에 집중할 수 있다. 사용자의 비용 우선순위에서는 이 구조로 bounded execution의 기본 품질을 Luna Max + Fast에서 확보하고, Sol의 추가 비용은 실제 오류 비용이나 독립성 요구가 정당화할 때 지불하는 편이 목적에 맞다. 모델 선택 순서를 명시하면 추상적인 최고 품질 선호가 예산 기준을 밀어내는 것을 막으면서도 중요한 작업의 상향 경로를 보존한다.

나중에 다시 볼 조건:

- Luna·Sol의 상대 가격, 성능 또는 가용성이 실질적으로 바뀐다.
- Fast의 사용량이나 서비스 계약이 바뀐다.
- 대표 실행 과제에서 Luna Max + Fast가 완료 기준을 반복해서 충족하지 못한다.
- 더 강한 모델로 상향하는 판단이 지나치게 잦거나 구체적인 근거 없이 이루어진다.
